# chuo 設計

要件定義書（`docs/requirements.md`）の要件を、どう実現するかを書く。プラグイン API の型とコードの書き方は `docs/plugin-api.md` にある。設計は要件定義書と矛盾させない。

## 1. 技術スタック

| 項目 | 採用するもの |
|---|---|
| ランタイム | .NET 10（LTS） |
| UI | Avalonia（その時点の最新安定版） |
| 本体の構成 | 汎用ホスト（`Microsoft.Extensions.Hosting`） |
| 本体のビルド | ReadyToRun（プラグインを動的に読み込むため、NativeAOT は使わない） |
| CLI クライアント | NativeAOT |
| 設定ファイル | JSON（`System.Text.Json`。読み込みは `Microsoft.Extensions.Configuration.Json`） |
| アプリが書き込むデータ | SQLite（`Microsoft.Data.Sqlite`） |
| CI と配布物の生成 | GitHub Actions |

### ソリューション構成

| プロジェクト | 役割 |
|---|---|
| `Chuo.Abstractions` | プラグイン API。NuGet でも配布できる形にする |
| `Chuo.Core` | 検索、インデックス、順位付け、プラグイン管理、プラットフォームの抽象インターフェイス |
| `Chuo.Platform.Windows` / `Chuo.Platform.Linux` | ホットキー、クリップボード、アプリ列挙などの OS ごとの実装。macOS 用は実装を空にしてビルドだけ通す |
| `Chuo.App` | Avalonia の UI と汎用ホスト（常駐する本体） |
| `Chuo.Cli` | NativeAOT でビルドする `chuo` コマンド（IPC クライアント） |
| `plugins/Chuo.Plugins.*` | 同梱プラグイン |
| `tests/` | テスト |

## 2. プラグインの読み込み

- プラグインは C# のクラスライブラリ（アセンブリ）とする。
- プラグインごとに collectible な `AssemblyLoadContext`（ALC）で読み込み、プラグイン単位でアンロードやホットリロードができるようにする。
- ホスト側の ALC と共有するアセンブリは、`Chuo.Abstractions` と `Microsoft.Extensions.*` に限る。それ以外の依存（NuGet 由来など）は、プラグインのフォルダ内のものをそのプラグインの ALC の中でだけ解決する。
- 本体は汎用ホストで構築する。プラグインごとに、専用の ALC の中で**ミニ汎用ホスト**（`Host.CreateEmptyApplicationBuilder`）を作る。
- プロバイダは、ホストが属性をスキャンし、プラグインの子コンテナから生成する。
- 常駐処理は `IHostedService` / `BackgroundService` で書く。
- 本体のサービスは、プラグインのホストにインスタンスを中継して登録する。
- アンロードは `StopAsync()`、`Dispose()`、`ALC.Unload()` の順に行う。
- 起動時はすべてのプラグインの `plugin.json` を読み、有効なものだけを読み込む。無効なものはコードを読み込まず、設定画面の一覧に名前とバージョンだけを出す。
- 有効と無効は `settings.json` の `plugins.<id>.enabled` に書く（値がなければ有効）。構成の再読み込みのたびに、前に反映した値と比べ、変わったプラグインだけを読み込むかアンロードする（読み込みに失敗したものを、設定を書き込むたびに読み直さないため）。
- プラグインの設定は `settings.json` の `plugins.<id>` のセクションを `IConfiguration` として渡し、`IOptionsMonitor<T>` で即座に反映する。

### 2.1 メタデータ

- パッケージの身元情報は、プラグインのフォルダの `plugin.json` に書く。承認時の表示や互換性チェックは、コードを実行せずにこのファイルで行う。
- 機能の定義（プロバイダの種類、キーワード、全体検索に含めるか）はコードの属性で行う。

### 2.2 信頼の検証

| 種別 | 置き場所 | 読み込みの条件 |
|---|---|---|
| 同梱プラグイン | 本体のフォルダの `plugins/` | ビルド時に埋め込んだハッシュと一致すること |
| ユーザーが追加したプラグイン | データフォルダの `plugins/` | 承認リストに記録された「プラグイン ID＋フォルダ全体のハッシュ」と一致すること |
| 開発中のプラグイン | 設定画面で明示的に登録したパス | ハッシュは検証しない。ホットリロードを有効にする |

- `chuo plugin add <フォルダ>` は、データフォルダへのコピーと承認をまとめて行う。

## 3. 検索

検索はカタログ型とライブクエリ型の 2 種類のプロバイダによるハイブリッド方式とする。

### 3.1 カタログ型

- 対象：アプリ、ファイル、クリップボード履歴など、項目の一覧を事前に作れるもの。
- プラグインは項目をホストに登録するだけで、検索はホストがメモリ上のインデックスに対して行う。
- 項目の更新は、プラグインが任意のタイミング（起動時、ファイル変更の監視時、定期実行時など）でホストに通知する。
- 全体検索に含めるか、キーワードを付けたときだけ検索対象にするかを属性で指定する。

### 3.2 ライブクエリ型

- 対象：電卓、Web 検索など、入力に応じて結果を動的に作るもの。
- 基本はキーワードを指定したときだけ呼ばれる。
- 入力がキーワードと同じ（空白なし）ときも、`Text` を空にして呼び、結果を全体検索の結果の上に混ぜる。打ちかけの語（例：`g` から `gimp`）を邪魔しないよう、空の入力で何も返さないプロバイダ（Web 検索、電卓）では見た目が変わらない。カタログ型は全件が出てしまうので対象にしない。
- グローバルトリガー（正規表現）を宣言した場合は、入力が一致したときだけ全体検索にも参加する。
- `CancellationToken` を必須とし、キー入力ごとに前のクエリをキャンセルする。プロバイダごとにタイムアウトを設ける。

### 3.3 順位付けと読み

- 順位付けはホストが一括で行う。
- カタログに項目を登録するときに、ホストが形態素解析で読み（かなとローマ字）を付与する。
- 辞書はインデックスを作るときだけ開き、終わったら破棄する。読みは SQLite にキャッシュし、辞書を常駐させない（技術検証 #6）。

## 4. プラットフォーム層

### 4.1 呼び出し

- ウィンドウは起動時に生成し、閉じるときは破棄せずに隠すだけにする。
- タスクトレイのアイコンは Avalonia の `TrayIcon` で出す（Windows は通知領域、Linux は D-Bus の StatusNotifierItem）。トレイのない環境では表示されないだけで、ほかの動作には影響しない。アイコンの画像は `src/Chuo.App/Assets/chuo.png`。

| 環境 | ホットキー | 前面化とフォーカス | 対応時期 |
|---|---|---|---|
| Windows | `RegisterHotKey` | `SetForegroundWindow`（ホットキー経由の呼び出しなので許可される） | 初版 |
| GNOME（Wayland） | 同梱の GNOME Shell 拡張（`Main.wm.addKeybinding`） | 同梱の GNOME Shell 拡張（`Main.activateWindow`） | 初版（挑戦） |
| Linux X11 | `XGrabKey` | `_NET_ACTIVE_WINDOW` | 後回し |
| Wayland（KDE / wlroots 系） | XDG Desktop Portal の `GlobalShortcuts` | 未定 | 後回し |

### 4.2 IME の制御

- Windows では、自分のウィンドウの入力コンテキストだけを制御する。IME が後から状態を復元するため、表示後しばらくは状態を監視してオフに戻す（技術検証 #3）。
- Linux では IBus（Fedora の既定）と Fcitx5 を D-Bus 経由で制御する。具体的な方式（入力コンテキストごとの制御か、Avalonia の入力目的のヒントを使うか）は試作で検証する。

### 4.3 クリップボードの監視

| 環境 | 監視方法 | 対応時期 |
|---|---|---|
| Windows | `AddClipboardFormatListener` | 初版 |
| GNOME（Wayland） | 同梱の GNOME Shell 拡張から D-Bus で通知を受ける（4.4） | 初版（挑戦） |
| Linux X11 | XFixes のイベント | 後回し |
| Wayland（KDE / wlroots 系） | data-control プロトコル | 後回し |

### 4.4 GNOME Shell 拡張

GNOME の Wayland では、アプリ側からはホットキーの登録、フォーカスの取得、ウィンドウの位置決め、クリップボードの監視ができない（または不確実である）。そこで、chuo に同梱する GNOME Shell 拡張に、GNOME Shell の内部でしかできない処理だけを任せる。

| 役割 | 拡張の中で使う API |
|---|---|
| グローバルホットキー | `Main.wm.addKeybinding` |
| ウィンドウの前面化とフォーカス | `Main.activateWindow` |
| ウィンドウの位置（マウスのあるモニタの中央など） | `MetaWindow.move_frame` |
| クリップボードの監視 | `St.Clipboard` と selection の変更イベント |

- 本体との通信は D-Bus で行う（本体側は `Tmds.DBus`）。
- 拡張は JavaScript で書く。C# だけで作るという方針の**唯一の例外**とし、ロジックはすべて C# 側に置く。拡張はイベントの中継と GNOME Shell の API 呼び出しだけを行う。
- GNOME のメジャー更新（約半年ごと）に追従する保守コストがかかるため、拡張の役割は上の表の範囲に限定する。

### 4.5 アプリの列挙

- Windows はスタートメニューの `.lnk` とパッケージのアプリ、Linux は `.desktop` からアプリを列挙し、アイコンも取得する。
- アプリを置いているフォルダの変更を `FileSystemWatcher` で監視し、変更が落ち着いてから（2秒後に）一覧を作り直す。
- Windows
  - 対象はユーザーと全ユーザーのスタートメニューの `.lnk` と `.url`。
  - `.lnk` は COM を使わずにファイルの形式（MS-SHLLINK）を直接読み、リンク先のパスを得る。リンク先は、サブタイトルと「ファイルの場所を開く」、実行ファイルの名前での検索に使う。
  - ユーザーと全ユーザーのスタートメニューの両方に同じアプリのショートカットがあると2件出るので、リンク先と引数（大文字と小文字は区別しない）が同じ `.lnk` は1つにまとめ、ユーザーのほうを残す。引数も比べるのは、同じ実行ファイルを引数違いで呼ぶショートカット（ブラウザのプロファイルごとのものや `rundll32.exe`）を残すため。リンク先の読めない `.lnk` と `.url` はまとめない。
  - 管理者としての実行は、`ShellExecute` の `runas` で行う。対象は実行ファイル（`.exe`、`.bat`、`.cmd`、`.com`、`.msc`）と、それを指すかリンク先の読めない `.lnk` とし、`.url` は対象にしない。UAC の確認を取り消したときは何もしない。キーは Windows の慣習（スタートメニューや「ファイル名を指定して実行」）に合わせて Ctrl+Shift+Enter とし、ホストがアクションの種類（`ItemActionKind`）で割り当てる。
  - パッケージのアプリ（Microsoft Store のアプリなど、`.lnk` を持たないもの）は、シェルの「アプリ」フォルダ（`shell:AppsFolder`）を `IShellItem` で列挙して得る。このフォルダには `.lnk` のあるアプリも並ぶので、AppUserModelID がパッケージの形（`<パッケージ名>_<発行元の ID>!<アプリの ID>`）のものだけを使う。項目の ID は AppUserModelID とし、起動とアイコンの取得には `shell:AppsFolder\<AppUserModelID>` を使う。管理者としての実行と「ファイルの場所を開く」は対象にしない。
  - パッケージの追加と削除は、`%LOCALAPPDATA%\Packages` の直下のフォルダの追加と削除で検知する（パッケージをユーザーに登録すると、パッケージごとのデータのフォルダができる）。中はアプリのデータで頻繁に変わるので、サブフォルダは監視しない。
  - アイコンはホストが `IShellItemImageFactory` で取得する。シェルの COM オブジェクトを安全に使うため、STA の専用スレッドで処理する。
- Linux
  - XDG のデータフォルダの `applications/` を優先度の順に読み、同じデスクトップファイル ID は優先度の高いものだけを使う。`NoDisplay`、`Hidden`、`OnlyShowIn` / `NotShowIn`、`TryExec` に従って除外する。
  - 起動は `gio launch` に任せる（端末で開くアプリや起動の通知も正しく扱える）。`gio` がなければ `Exec` を直接実行する。
  - アイコンは hicolor と Adwaita のテーマ、`/usr/share/pixmaps` から PNG を探す。使用中のアイコンテーマには従わず、SVG にしかないアイコンは表示できない。

### 4.6 自動起動

- Windows は、ユーザーの Run キー（`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`）の `chuo` に、今の実行ファイルのパスを引用符で囲んで書く。管理者の権限は要らない。引数を付けないので、ランチャーを隠したまま常駐する。
- 値は `settings.json` には持たず、レジストリだけを正とする（OS の画面で変えたときとずれないようにするため）。
- タスクマネージャーの「スタートアップ アプリ」で無効にすると、Run キーの値は残ったまま、`HKCU\...\Explorer\StartupApproved\Run` の `chuo` の先頭のバイトが奇数になる。この場合はオフとして扱い、オンにするときはこの値を消す。
- 別の場所の chuo（展開し直した zip や開発中のビルド）が登録されていれば、設定画面ではオフとして表示し、登録されている場所を出す。オンにすると今の chuo に置き換える。起動時に勝手に置き換えることはしない。
- Linux は未対応（XDG の autostart を使う予定）。

## 5. `chuo` コマンドと IPC

- `chuo` コマンドは NativeAOT でビルドした軽量クライアントとする。
- IPC は `NamedPipeServerStream`（Windows では名前付きパイプ、Unix ではドメインソケットとして動く）で行う。

## 6. 項目とユーザー設定のデータ

- 項目の ID はプラグイン内で一意で、再起動しても変わらない値とする（例：`.desktop` のパス、AppUserModelID、ファイルのフルパス）。
- グローバルな識別子は `<pluginId>:<itemId>` とする。使用履歴、エイリアス、お気に入り、無視の設定で共通に使う。
- 項目ごとのユーザー設定は `items.json` にまとめて保存する。

```json
{
  "chuo.apps:firefox.desktop": { "aliases": ["ff", "web"], "favorite": 1 },
  "chuo.apps:uninstall-foo.desktop": { "ignore": true }
}
```

- `items.json` は設定のフォルダに置く。アプリは書き込む直前に読み直し、手で書いた値（今は使っていないキーなど）を消さない。読めないときは上書きせずに失敗させる。手で編集したときは、ファイルの監視で読み直す。
- 識別子の大文字と小文字は区別する（項目の ID がファイルのパスのことがあるため）。
- `favorite` はお気に入りの表示順を表す。追加したものは末尾に付け、外したらキーを消す。
- お気に入りには、順位付けで一定の点（連続した一致の減点の最大より大きい値）を足す。一致の度合いが近ければお気に入りが上に来るが、あいまいな一致しかしないお気に入りが、連続して一致する項目を超えるとは限らない。
- 入力が空のときのお気に入りの一覧と `:ignored` の一覧は、識別子からカタログの項目を引いて作る。ライブクエリの結果はカタログにないので、お気に入りにしても入力が空のときの一覧には出ない。カタログにない無視した項目は、`:ignored` に識別子だけを出す。
- お気に入りと無視の操作は、ホストがすべての項目に付ける。右クリックのメニューには、項目のアクション（割り当てたキーを添える）の下に、これらの操作を並べる。
- アクションパネルは、右クリックのメニューと同じ並び（項目のアクション、区切り、ホストの操作）を、結果の一覧の代わりに出す。見出しは項目のタイトルだけにする。
  - 入力の末尾にカーソルがあり、何も選択していないときの → で開く。それ以外の → はカーソルを動かす。
  - ↑↓ で選び、Enter で実行する。← か Esc で結果の一覧に戻る。文字を打つとパネルを閉じて検索に戻る。Ctrl の付いたキー（Ctrl+D など）は、パネルを閉じてから通常どおり扱う。
  - アクションの中身はプラグインが項目ごとに決める（`ResultItem.Actions`）。ホストはそれを並べるだけで、パネルのための API は足さない。
- エイリアスは入力と同じ正規化（3.3）をして比べる。カタログ型の項目だけに効く（ライブクエリの結果は毎回作られるので対象にしない）。
  - 完全一致は固定の大きな点にし、ライブクエリの結果より上に置く。1つのエイリアスに複数の項目が一致したときは、今は名前の順に並べる（使用履歴を作ったら、その順にする）。
  - 前方一致は、お気に入りより大きな点を足す。補った文字が少ないエイリアスほど上にする。前方一致したエイリアスを補完（8 章）に出し、Tab で入れられるようにする。
  - あいまいな一致をしない項目でも、エイリアスが一致すれば結果に出す。無視した項目は出さない。
- エイリアスはダイアログで、空白で区切って編集する。前後の空白を除き、重複（大文字と小文字は区別しない）を捨て、1つもなければ `aliases` のキーを消す。
- 無視の glob パターンはグローバルな識別子に対して照合する（例：`chuo.apps:*uninstall*`）。無視の判定はホストが行い、カタログ型とライブクエリ型の両方の結果に適用する。

## 7. ファイル検索

- 自前のインデックスを持つ。起動時にスキャンし、その後は `FileSystemWatcher` で差分を反映する。

### 7.1 Daily Folder

- ライブクエリ型のプロバイダ1つ（キーワード `daily`）で受ける。入口を1つにし、設定のキーワードも1つにする（以前は全体検索の項目を別のカタログ型で出していたが、キーワードとエイリアスの区別が分かりにくかった）。
  - `daily` だけなら、今日のフォルダの項目（先頭なので Enter で開く）、今日より前のフォルダを新しい順に 5 件、サブコマンドの一覧（補完付き）の順に出す。
    - 直近のフォルダのアクションは、開く（Enter）、保持の切り替え（Ctrl+Enter）、ごみ箱に移す、パスをコピー。残りはアクションパネルから選ぶ。保持しているものはタイトルに ★ を付ける。
    - ごみ箱に移したフォルダは保持からも外す。移せなかったときは、prune と同じく次の一覧の先頭に知らせを出す。
  - `daily prune` では、先頭に「N 件のフォルダをごみ箱に移す」の項目を、その下に削除するフォルダを並べる。先頭の項目の Enter で実行し、フォルダの項目の Ctrl+Enter で保持する。
  - `daily keep` では、フォルダを新しい順に並べ、Enter で保持を切り替える。後ろに文字を付けると、名前で絞り込む。
- 既定の置き場所は、ドキュメントのフォルダ（`Environment.SpecialFolder.MyDocuments`）の中の `Daily`。Linux でドキュメントのフォルダが決まっておらずホームが返るときは、`~/Documents/Daily` にする。設定を空にしたときも既定の場所を使う。
- 扱うのは、名前が日付の書式（既定は `yyyy-MM-dd`）に合うフォルダだけ。ほかのフォルダには触れない。
- 「残す日数」が N なら、今日を含めた N 日分を残し、それより前の日付のフォルダを削除の対象にする。
- 保持したフォルダの名前は、プラグインのデータのフォルダの `kept.json` に保存する。プラグインは `settings.json` に書き込めないため。
- ごみ箱へは、Windows では `Microsoft.VisualBasic.FileIO.FileSystem.DeleteDirectory`（`RecycleOption.SendToRecycleBin`）、Linux では `gio trash` で移す。移せなかったフォルダは削除せずに残し、次の一覧の先頭に知らせを出す。
- 操作の後は、`ActionResult.SetQuery` で同じ入力を返して一覧を作り直す。ホストは、入力が変わらなくても検索し直す。

## 8. UI

- 文言は短くし、長い文章を読まなくても操作できるようにする。ラベルで分かることには説明を付けず、付けるときも短い句にする。仕組みの説明は画面に書かず、文書に書く。
- プラグインは UI のコントロールを返さない。プレビューや設定画面は、プラグインが返す宣言的なデータからホストが描画する。
- プレビューは項目を選択したときに初めて取得する。型は `docs/plugin-api.md` を参照。
- 補完は項目が持つ（`ResultItem.Completion`）。値はキーワードを除いた検索の文字列で、ホストが検索に使ったキーワードの部分を前に付けて入力欄の文字列にする。選んでいる項目の補完が入力で始まり（大文字と小文字は区別しない）、カーソルが末尾にあって範囲を選んでおらず、IME で変換していないときだけ、続きを薄く表示する。Tab を押すと補完で入力欄を置き換える。
- 補完の続きは、入力欄のテンプレートの中で文字を描く `TextPresenter` の隣に `TextBlock` を足して描く。入力した部分を透明な文字で並べて幅を取り、続きを入力の後ろにそろえる。フォントと横のスクロールは入力欄と同じになる。
- 設定画面は、常駐するメモリを増やさないため、開いたときに生成し、閉じたら破棄する。閉じた後、ランチャーが隠れていればメモリを OS に返す。
- 設定画面は、左に本体のページ（一般、項目）とプラグインの一覧、右に選んだページを置く。
- 項目のページには、エイリアスを付けた項目の一覧（編集と削除）と、無視した項目の一覧（無視の解除）を出す。名前は `:ignored` と同じくカタログから引き、見つからない項目（プラグインを無効にした、外したなど）は識別子を出す。`items.json` が変わったら（ランチャーでの操作や手での編集）作り直す。ページには、プロバイダごとのキーワードと全体検索に含めるか、プラグインの設定を並べる。
- テキストの入力は、打ち終わってから（0.5秒後、またはフォーカスを外したときに）書き込む。値が変わったときだけ書き込む。
- プラグインの設定画面は、ホストが Options クラスのプロパティと属性から自動で生成する。属性は `System.ComponentModel.DataAnnotations` を使い、標準の属性で表せないもの（フォルダやファイルの選択など）は独自の属性を用意する。対応していない型のプロパティがある場合、ホストは読み込み時に警告を出す。
- 要素ごとに値を持つリストは、要素を設定のクラスにした `List<T>` で表す。ホストは要素のクラスも同じ規則で読み、最初の文字列かパスの値を要素の代表として一覧に出し（重複の判定にも使う）、残りの値の入力欄をその下に並べる。要素の中のリストには対応しない。
- 同梱プラグインで共有するコード（`.lnk` や `.desktop` の読み取り）は、ALC が別々なので共有のアセンブリにはせず、`plugins/Shared/` のソースを各プラグインに取り込む。

## 9. 設定とデータのファイル

| 種類 | ファイル | 編集方法 |
|---|---|---|
| 設定 | `settings.json` | 設定画面で編集する。手で編集することもでき、保存すると自動で再読み込みされる |
| 項目ごとのユーザー設定 | `items.json` | アプリが書き込む。手で編集することもできる |
| 使用履歴、承認リスト | SQLite | アプリのみが書き込む |
| ログ | `logs/` | アプリが書き込む。日ごとにファイルを切り替え、プラグインごとにカテゴリを分ける |

- アプリが設定ファイルを書き込むときは、一時ファイルに書いてから置き換える。
- 設定のキーを消したときは、空になった親のオブジェクトも消す。
- 設定画面での変更は `settings.json` に書き込み、構成の再読み込み（`reloadOnChange`）を通じて `IOptionsMonitor` で本体とプラグインに反映する。自分の書き込みでも再読み込みが走るが、反映の経路を1つにするため、それでよいとする。
- `settings.json` のプラグインの部分は次の形にする。キーの大文字と小文字は区別しない。

```json
{
  "plugins": {
    "chuo.shortcuts": {
      "enabled": true,
      "settings": { "folders": [{ "path": "C:\\Users\\me\\Tools", "includeSubfolders": true }] },
      "providers": { "ShortcutCatalogProvider": { "keyword": "l", "includeInGlobal": false } }
    }
  }
}
```

  - `enabled`：プラグインを有効にするか。値がなければ有効。
  - `settings`：プラグインの設定。プラグインに `IConfiguration` として渡す。
  - `providers`：プロバイダごとのキーワードと全体検索に含めるかの上書き。値がなければ、プロバイダの属性の値を使う。キーワードを空文字列にすると、キーワードなしになる。

| OS | 設定 | データ |
|---|---|---|
| Linux | `~/.config/chuo/` | `~/.local/share/chuo/` |
| Windows | `%APPDATA%\chuo\` | `%APPDATA%\chuo\` |

## 10. インストール

| 処理 | Windows | Linux |
|---|---|---|
| 自動起動の登録 | `HKCU\...\Run` | `~/.config/autostart/chuo.desktop` |
| PATH への追加 | ユーザーの PATH に追加 | `~/.local/bin` にシンボリックリンクを作成 |
| アプリ一覧への登録 | — | `.desktop` を登録 |
| GNOME Shell 拡張 | — | GNOME の環境では、拡張をインストールして有効化する |

- 配布するアーカイブには、chuo 自身とプラグインの pdb を含める（ログに出す例外のスタックトレースに、ファイル名と行番号を出すため。合わせて 200KB ほど）。SkiaSharp と HarfBuzzSharp のパッケージに入っているネイティブの pdb（合わせて約 100MB）は、ネイティブのクラッシュダンプの解析にしか使わないので含めない。

### 10.1 CI とリリース

- GitHub Actions で行う。ワークフローは `.github/workflows/` にある。
- `ci.yml`：`main` への push とプルリクエストで、Windows と Linux の両方でビルドとテストを行う。
- `release.yml`：`v` で始まるタグ（例：`v0.1.0`）を push すると、テストしてから Windows 向けに発行し、`chuo-<バージョン>-win-x64.zip` をリリースに添付する。
  - バージョンはタグから取り、`-p:Version` で実行ファイルに埋め込む。`v0.2.0-beta.1` のようにハイフンを含むものはプレリリースにする。
  - リリースノートは GitHub の自動生成（`--generate-notes`）を使う。
  - Linux 向けの配布物は、Linux で使えるようになってから（ホットキーなど、4.4）足す。
